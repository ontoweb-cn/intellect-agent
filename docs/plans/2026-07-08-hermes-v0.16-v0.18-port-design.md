## 一、背景与目标

intellect-agent 与 hermes-agent 同源，历史上通过周期性移植（cherry-pick + 品牌适配）跟进上游功能。
上一轮移植基线为 hermes 2026-05-31 每日更新（对应 v0.16.0 发布前窗口）。本文档：

1. 梳理 hermes-agent **v0.16.0（2026-06-06）→ v0.17.0（2026-06-19）→ v0.18.0（2026-07-01）** 的主要功能变化；
2. 对照 intellect-agent v0.6.7 现状，识别功能差距；
3. 结合 intellect-agent 的两大架构差异，给出移植/自研设计方案：
   - **无独立 Desktop 客户端** — hermes 有 `apps/desktop/`（Electron 桌面应用）+ web dashboard；
     intellect 有 `webui/`（Web 仪表盘）+ TUI，但没有 Desktop 应用。Desktop 专属功能需落到
     CLI / TUI / WebUI 三个既有表面，或者放弃；
   - **Rust 与 Python 协同实现** — agent loop 主体在 Python，外围热路径（存储、沙箱、加密、
     流解析、Gateway 调度）已迁移至 Rust（`intellect_community_core`，迁移率约 20%）。
     **新功能从设计之初就要划定 Rust/Python 边界**，避免先写 Python 再二次迁移。

本文档形成后提交评审，评审通过后拆解为实施计划。

## 三、Intellect Agent 现状差距矩阵

基于对 intellect-agent v0.6.7 源码的调研（2026-07-08）：

| # | Hermes 功能 | Intellect 现状 | 差距 | 移植价值 |
|---|-------------|----------------|------|----------|
| 1 | MoA 虚拟 provider（`moa/<preset>`） | 仅有 `mixture_of_agents` **工具**（`tools/mixture_of_agents_tool.py`），默认关闭，依赖 OpenRouter | 工具 ≠ 模型；无法作为主模型/辅助模型选中 | 高 |
| 2 | 验证证据台账 + verify-on-stop | `/goal` 已有成熟 Ralph 式循环 + LLM judge（`intellect_cli/goals.py`），但**无证据台账**，judge 仅凭对话内容 | 缺证据存储与 verify 钩子；judge 判定无 grounding | 高 |
| 3 | `/learn` 技能蒸馏 | 无。已有 `background_review.py`（后台自动改进技能）+ curator | 缺用户主动触发的会话→技能蒸馏 | 高 |
| 4 | `/journey` 学习图谱 | 无 | 全缺 | 中 |
| 5 | 后台委派（`background=true` + 扇出） | `delegate_task` 同步阻塞（**有意设计**）；`tools/process_registry.py` 已有但仅服务 terminal 后台进程 | 缺异步委派注册表与完成事件回流 | 高 |
| 6 | Gateway scale-to-zero + relay | 已有优雅 drain（`gateway/run.py` `_draining`）；无 scale-to-zero、无 relay | 部分缺 | 中 |

| 8 | 按通道模型覆盖 | 仅有会话级 `/model` 覆盖（`_session_model_overrides`） | 缺 config 级 per-platform/per-channel 覆盖 | 中 |
| 9 | Automation Blueprints | 无；cron 本体成熟（`cron/jobs.py`, `cron/scheduler.py`） | 全缺 | 高 |
| 10 | WhatsApp Cloud API | 仅 web bridge（Node 子进程） | 缺官方 Cloud API 适配器 | 中 |
| 11 | 图像编辑（源图→编辑端点） | 纯文生图；`ImageGenProvider` ABC 无 `edit()` | 全缺 | 中 |
| 12 | Memory 批量操作 | `memory` 工具单 action API | 缺 `operations` 数组 | 中（低成本） |
| 13 | Secret sources / 1Password | 框架已有（`agent/secret_sources/`），仅 Bitwarden | 缺 1Password 后端 | 低-中 |
| 14 | Google Vertex AI provider | 29 个 provider 插件，无 Vertex | 缺 | 中 |
| 15 | Photon iMessage | 已有 BlueBubbles（gateway + plugin 双实现） | iMessage 已覆盖，通道不同 | 低（跳过） |
| 16 | Raft 代理网络 | 无同类；多代理协作走 kanban，去中心化消息走 SimpleX | 定位重叠部分已有替代 | 低（暂缓） |
| 17 | Desktop Projects / Star Map / Desktop 深化 | 无 Desktop 客户端；已有 members/projects 体系（P6–P11）+ WebUI | Desktop 专属不适用；Projects 语义 intellect 已有 | 不移植（映射到 WebUI） |
| 18 | Pets | 无 | 趣味功能 | 低（可选） |
| 19 | Chronos 托管 cron | 无；cron 内置 scheduler | 依赖 scale-to-zero 才有意义 | 低（随 #6） |

> 真正缺失的是 hermes 的 **Desktop 桌面应用**（`apps/desktop/`, Electron）。本方案按此事实处理：
> hermes Desktop 专属功能一律不移植，其中有独立价值的部分（如 /journey 可视化）落到 WebUI。

## 四、架构约束与设计原则

### 4.1 表面层约束（无 Desktop）

hermes 新功能凡涉及 UI 的，intellect 需覆盖三个表面：

| Hermes 表面 | Intellect 对应 |
|-------------|----------------|
| Desktop（Electron） | **无 → WebUI 承接**（可视化类）或放弃（原生通知/快捷键类） |
| CLI（rich + prompt_toolkit） | CLI（同构，slash 命令经 `COMMAND_REGISTRY` 中央注册表） |
| TUI（Ink + tui_gateway） | TUI（同构） |
| Web dashboard | WebUI（`webui/`） |
| Gateway 平台 | Gateway 平台（同构） |

新增 slash 命令必须走 `intellect_cli/commands/registry.py` 中央注册表（CLI/Gateway/Telegram/
Slack/补全/帮助自动派生），并遵守 **缓存感知** 原则（默认延迟生效 + `--now` 选项）。

### 4.2 Rust/Python 分工原则

延续 `docs/architecture/rust-python-interaction.md` 的既定边界，新功能按以下规则切分：

| 归 Rust（`intellect_community_core`） | 归 Python |
|----------------------------------------|-----------|
| SQLite 存储读写（新表复用 `SQLiteBackend`） | LLM 调用、provider SDK 交互 |
| 纯计算/纯数据变换（解析、校验、归一化、评分） | 工具编排、插件加载（动态性） |
| 安全检测（模式匹配、脱敏） | Gateway 平台 I/O、UI |
| 并发原语（注册表、调度器、计数器） | 业务策略与配置逻辑 |

**新功能的落地要求**：涉及新持久化状态的（验证台账、委派注册表、学习图谱、蓝图目录），
schema 与读写路径 **直接在 Rust 层实现**，Python 只拿到薄封装。这与存量代码"先 Python
后迁移"的路径相反，是本轮设计的关键差异——避免制造新的迁移欠账。

### 4.3 既有政策红线

- 插件不得修改核心文件；`plugins/memory/` 不再收新 in-tree provider；
- 依赖必须有版本上界（供应链政策）；
- 不破坏 prompt caching（禁止会话中途改系统提示/工具集）；
- delegate_task 非持久化的定位不变——后台委派仍不跨回合持久（见 §5.3 设计）。

## 五、分项设计方案

按优先级分组：P0（高价值/低风险，本迭代）、P1（高价值/中风险，下迭代）、P2（选做/依赖前置）。

---

### 5.1 [P0] Memory 工具批量操作

**目标**：`memory` 工具支持 `operations` 数组，一次调用原子执行多个 add/replace/remove。

**方案**：
- `tools/memory_tool.py` schema 增加可选 `operations: [{action, ...}, ...]` 参数；
  存在 `operations` 时忽略顶层单 action 参数；
- 原子性：先在内存中对 `MEMORY.md`/`USER.md` 内容依序应用全部操作、逐条校验
  （replace/remove 目标不存在即整批失败），全部通过后一次写盘；
- 返回逐条结果 + 总结。

**Rust/Python 分工**：文件极小（KB 级 Markdown），纯 Python 实现，无 Rust 必要。

**涉及文件**：`tools/memory_tool.py`、`tests/tools/test_memory_tool.py`。
Memory-provider 插件（honcho/mem0 等）不受影响——批量操作只作用于文件后端；
`MemoryProvider` ABC 不改。

**风险**：低。工具 schema 变化对模型透明（新增可选参数）。

---

### 5.2 [P0] 按通道模型覆盖（Gateway）

**目标**：config 级 per-platform / per-channel 模型覆盖，与现有会话级 `/model` 覆盖叠加。

**方案**：
- `config.yaml` 新增：

```yaml
gateway:
  model_overrides:
    telegram: { model: "...", provider: "..." }
    "telegram:<chat_id>": { model: "..." }   # 通道级，可选
    discord: { model: "..." }
```

- 解析优先级：会话级 `/model` 覆盖 > 通道级 > 平台级 > 全局默认；
- 落点：`gateway/agent_runner.py` 构建 AIAgent 参数处，与 `_session_model_overrides`
  同一分辨函数内合并；`gateway/config.py` + `intellect_cli/config.py` `DEFAULT_CONFIG`
  增加键（注意三条 config 加载路径都要覆盖，见 AGENTS.md "Config loaders"）。

**Rust/Python 分工**：纯配置分辨逻辑，Python。若后续 `rust_build_session_key` 需要感知
覆盖键，可在 `gateway.rs` 增加通道键规范化函数（非必须）。

**风险**：低。注意 per-channel 键格式与 `build_session_key` 的键空间保持一致。

---

### 5.3 [P0→P1] 后台委派（background delegation + 扇出）

**目标**：`delegate_task(background=true)` 立即返回句柄；子代理完成后，结果作为整合回合
回流父会话。多个后台子代理可并行（扇出），结果合并进同一个回合。

**方案**：
- 新增 `tools/async_delegation.py`：后台委派注册表，管理 `DelegationHandle`
  （id、goal、状态、启动时间、结果摘要）；
- 复用现有两块基础设施：
  - `tools/process_registry.py` 的事件回流模式（gateway watcher 检测完成→触发新回合），
    hermes 正是走 `process_registry` 共享事件通道；
  - `delegation.max_concurrent_children` 并发上限对后台委派同样生效；
- `delegate_task` schema 增加 `background: bool = false`；`role="leaf"` 限制不变；
- 完成事件在 CLI 表面表现为下一次输入前的通知 + `/bg` 命令查询状态（新增 CommandDef）；
  在 gateway 表面复用 `display.background_process_notifications` 的分级配置；
- **生命周期边界（与 hermes 的差异，保留 intellect 既有立场）**：后台子代理仍属于当前
  进程生命周期，不做跨进程持久化。进程退出即终止，schema 描述继续指引"需要跨回合持久
  的工作用 `cronjob` 或 `terminal(background=True)`"。这样不违背既有 "delegate_task 非
  durable" 政策，只是把"父回合内阻塞等待"放宽为"父回合结束后异步回流"。

**Rust/Python 分工**：
- 子代理执行本体（AIAgent fork）必须在 Python；
- **注册表状态机放 Rust**：`rust-core/src/delegation.rs` 实现 `DelegationRegistry`
  （线程安全 Mutex 注册表、句柄分配、状态迁移、完成队列 drain），与
  `PlatformRetryScheduler` 同一模式（Stage 4 已验证该模式可行）。Python 侧线程只在
  完成时调用 `registry.complete(handle, summary)`；
- 事件的消费（组装整合回合的 prompt）在 Python。

**涉及文件**：`tools/delegate_tool.py`、`tools/async_delegation.py`（新）、
`rust-core/src/delegation.rs`（新）、`intellect_rust.py`、`gateway/agent_runner.py`、
`intellect_cli/commands/registry.py`（`/bg`）、`cli.py`。

**风险**：中。主要在完成事件与 gateway 双重消息 guard 的交互（见 AGENTS.md "TWO message
guards" 陷阱）——完成回流必须走与 `notify_on_complete` 相同的已验证路径。父代理中断时
后台子代理的取消语义需要明确（建议：父会话 `/stop` 默认不取消后台子代理，`/bg cancel <id>`
显式取消）。

---

### 5.4 [P1] 验证证据台账 + `/goal` 完成契约

**目标**：编码类工作可记录"验证证据"（测试运行、命令输出、diff 校验）；`/goal` 的 LLM
judge 判定时以证据台账为 grounding，而非仅凭对话文本；回合结束时若有未验证的声明，
注入 verify-on-stop 提示。

**方案**（三层）：
1. **证据台账** `agent/verification_evidence.py`：
   - SQLite 表 `verification_evidence(id, session_id, task_id, kind, command, exit_code,
     summary, artifact_path, created_at)`；
   - 写入时机：`terminal` 工具执行测试/构建类命令后（由结果分类器判定 kind）、
     文件 mutation landed 检测通过后（`rust_file_mutation_landed` 已有）；
2. **verify-on-stop** `agent/verification_stop.py`：
   - 回合将结束（无 tool call 的最终响应生成前）时，若本回合有代码修改但台账中无对应
     证据，构建一次 nudge（"你修改了 X 但未运行验证，请验证或明确说明跳过原因"）；
   - 与现有 goal judge 循环（`intellect_cli/goals.py`）串联：judge 的 prompt 注入台账
     摘要，实现"依据证据判定契约完成"；
   - 配置门控 `agent.verification.enabled`（默认 false 起步，稳定后翻转），避免打扰
     非编码场景；
3. **`/goal` 契约扩展**：`/goal` 语法允许附带完成契约（如 "tests pass"），judge 判定时
   将契约与证据 kind 匹配。

**Rust/Python 分工**：
- **表 schema + 读写在 Rust**：`rust-core/src/verification.rs`，复用 `SQLiteBackend`
  连接与 WAL 模式，导出 `record_evidence_rs` / `query_evidence_rs`；
- **证据分类（何种命令算验证）在 Rust**：模式匹配正则表（pytest/cargo test/npm test/

### 5.9 [P2] Gateway 生产化三件套（scale-to-zero / relay / 异步存储）

hermes 的三个 gateway 特性有内在依赖，intellect 按收益重排：

**5.9.1 异步会话存储 — 走 Rust 路线而非 AsyncSessionDB 移植**

hermes 的 `AsyncSessionDB` 是 Python asyncio 包装。intellect 的读写已在 Rust
`SQLiteBackend`（`SESSIONDB_USE_RUST_RW=1` 默认启用），正确路线是：
- `backend.rs` 写路径已释放 GIL（rusqlite 调用期间）；补齐读路径 GIL 释放审计；
- 为 gateway 高并发场景在 Rust 侧增加 **写合并队列**（批量 flush 消息，对应
  optimization-roadmap P9 的 schema 依赖项，一并解决）；
- **不引入 Python asyncio DB 层**——gateway 的 asyncio event loop 通过
  `run_in_executor` 调用同步薄封装即可，避免双事件循环复杂度。

**5.9.2 scale-to-zero**

- 在现有 drain 基础上增加：空闲超时（无活跃会话 X 分钟）→ gateway 自停；
  唤醒依赖平台侧（webhook 类平台天然支持；长轮询类平台如 Telegram polling 不适用
  scale-to-zero，配置校验时明确拒绝）；
- systemd socket activation 作为守护路径（`deploy/` 已有 systemd 资产可扩展）；
- Chronos 类托管 cron **不移植**——intellect 部署形态以常驻为主，scale-to-zero
  为可选优化，配置门控 `gateway.scale_to_zero.enabled`（默认 false）。

**5.9.3 relay 连接器**

- gateway 间消息转发（一个 gateway 作为另一个的上游通道）。intellect 当前多实例
  隔离靠 profiles + kanban，relay 的真实需求待定——**建议本轮仅做需求调研，不实施**。

**风险**：中-高（5.9.1 中）。写合并涉及崩溃一致性；5.9.2/5.9.3 依赖部署形态反馈。
